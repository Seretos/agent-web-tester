# agent-web-tester

Skill + inline MCP wrapper plugin — no bundled binary, but both host manifests declare an inline `mcpServers.playwright` server. Ships `skills/web-tester/SKILL.md`, which Claude Code loads when the skill's `description` matches the user's intent, backed by a live, headed browser via `@playwright/mcp`.

## Contracts an agent won't infer from the tree

- **Release is orphan-branch + marketplace dispatch.** `release.yml` (manual: Actions → release → `version=X.Y.Z`) stamps the version, then force-pushes an orphan `release` branch holding only install-ready files and POSTs a dispatch (`category: skill`) to `Seretos/agent-marketplace`. `main` and `release` share no history. Clients install at the tag `agent-web-tester--vX.Y.Z`.
- **Required secret:** `MARKETPLACE_DISPATCH_TOKEN` — fine-grained PAT, `Contents: RW` + `Pull requests: RW` on `Seretos/agent-marketplace` only.
- **`assets/icon.png` is a release artifact, not just a repo file.** The dispatch payload sends a `raw.githubusercontent.com/${repo}/${TAG}/assets/icon.png` URL to the marketplace, so the file must live on the orphan `release` branch at the tagged commit — `release.yml`'s stage step copies `assets/` into the staging tree for exactly that reason. Ship `assets/icon.png` from day one or the marketplace listing has no image.
- **`description.md` is a release artifact, not just a repo file.** The dispatch payload sends a `raw.githubusercontent.com/${repo}/${TAG}/description.md` URL in the `description_url` field, so the file must live on the orphan `release` branch at the tagged commit — `release.yml` copies it into the staging tree alongside `assets/`. Fill in its Key Features before cutting v0.0.1.
- **`docs/` is a release artifact too, not just a repo directory.** Everything under `docs/` ships on the orphan `release` branch the same way `assets/` and `description.md` do — `release.yml`'s stage step copies it into the staging tree — because `agents/page-scanner.md` points installed users at `docs/examples/todomvc-scan.md` as its worked-example template. Do not park internal notes under `docs/`; anything placed there ships to every installed user.
- **Note: subagents are a Claude-Code-only, convention-discovered feature.** Claude Code loads every `<plugin-root>/agents/*.md` file by directory convention, with no manifest entry required — so neither `.claude-plugin/plugin.json` nor `.codex-plugin/plugin.json` gets an `agents` key, and the byte-identical-manifest contract for `mcpServers.playwright` stays intact. `release.yml`'s stage step still has to copy `agents/` into `$STAGE` explicitly (the convention only covers discovery once the directory is present, not staging).
- **Depending on an MCP plugin:** declare it under `dependencies` in `.claude-plugin/plugin.json` (`{ "name": "agent-<mcp>", "version": ">=0.0.1 <1.0.0" }`); Claude Code installs/loads it automatically with this skill.
- **The live browser is `@playwright/mcp`, launched via inline `npx` — no wrapper script.** Both `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json` carry a byte-identical `mcpServers.playwright` block: `{"command": "npx", "args": ["-y", "@playwright/mcp@0.0.79", "--browser", "chromium"]}`. Unlike `agent-serena-wrapper` or `agent-chrome-wrapper`, there is no `${CLAUDE_PLUGIN_ROOT}`/`${PLUGIN_ROOT}` and no `scripts/` directory — those exist only to spawn a repo-local boot wrapper, and this package deliberately has none, so both manifests resolve to the exact same block.
  - **Exact pin, no ranges.** The `@playwright/mcp@X.Y.Z` arg is an exact version — never `latest`, never a `^`/`~` range, never a pre-release tag. Bumping the pin means editing the version string in **both** manifest files and re-running this stdio handshake before merging:
    ```
    printf '%s\n' \
     '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"handshake","version":"0"}}}' \
     '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
     '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \
     | npx -y @playwright/mcp@<PIN> --browser chromium
    ```
    Pass criteria: `initialize` returns a result with `serverInfo`, and `tools/list` includes both `browser_navigate` and `browser_snapshot`.
  - **Headed by default, by omission.** `@playwright/mcp` runs headed unless `--headless` is passed; there is no separate `--headed` flag to opt back in with. The manifests simply never pass `--headless` — that omission *is* the headed decision. Do not add `--headless` to either manifest.
  - **Default persistent profile, by omission.** Neither `--user-data-dir` nor `--isolated` is passed. The server's own default profile directory (persistent, keyed per-workspace) is used as-is; don't invent a plugin-specific profile path.
  - **`--browser chromium` selects Playwright's bundled Chromium, not the user's Chrome.** Without this flag the server's default browser is the `chrome` channel (the user's installed Google Chrome), which is not what this plugin wants. `--browser chromium` resolves to the Playwright-managed Chromium build instead (confirmed by reading `resolveBrowserParam` in the installed `playwright-core` — `"chromium"` maps to `{ browserName: "chromium", channel: "chrome-for-testing" }`, distinct from `"chrome"`). Note the pinned version's own `--help` text lists only `chrome, firefox, webkit, msedge` as "possible values" for `--browser` — that enum is incomplete documentation, not a real restriction; `"chromium"` is a fully supported value, per the package's own README (its Docker example uses `--browser chromium`) and per source. On a machine that has never run Playwright's browser install, the first `browser_navigate` call may report a missing browser; the fix is the server's own `browser_install` MCP tool — do not add a provisioning script for this.
  - **Why `@playwright/mcp` and not the sibling `agent-chrome-wrapper` plugin.** `agent-chrome-wrapper` connects to (or launches) the user's actual installed Chrome via CDP, which is the right shape for driving a human's real, already-logged-in browser session. This plugin exists for a different job: authoring and recording E2E test scenarios headlessly-capable-but-headed-by-default, with a disposable, Playwright-managed browser (bundled Chromium, not the user's Chrome profile) that stays isolated from the user's day-to-day browsing — so a test run can't accidentally touch the user's real cookies, extensions, or open tabs, and multiple parallel test sessions don't fight over the same browser instance. `@playwright/mcp` is Microsoft's own MCP server built exactly for that: structured accessibility-tree snapshots, navigation, and interaction tools tailored to scripted test authoring rather than general browsing.
- **`skills/` is staged wholesale.** `release.yml`'s stage step already does `cp -a skills/. "$STAGE/skills/"` before `zip -r`, so a new skill directory under `skills/` needs no `release.yml` edit — unlike `agents/` and `docs/`, which each needed their own explicit `cp -a` line.
- **`scaffold-bdd` writes into the target repo under test, never into this repo.** This repo deliberately carries no committed `e2e/` tree; `docs/examples/scaffold-bdd-run.md` is the only mirror of what the skill produces, kept honest by `.github/scripts/validate_scaffold.py`.
- **`page-scanner`'s hard-rule literals are pinned byte-for-byte** in `.github/scripts/validate_agents.py`; amending a rule (as this ticket does to `D2`) means editing the agent file and the validator in the same commit.
- The catalog's three columns carry **no** Gherkin keyword — the keyword is derived from the phrase text by `scaffold-bdd`'s `G2`, and the `e2e/**` layout in `P3` is the path contract that packages #4 and #5 bind to. Changing either breaks a downstream package, not just this one.
- The scaffolded demo is deliberately one step definition, one catalog row, and one feature line, because `page-scanner` regenerates one catalog row per step definition — growing the demo silently grows every scaffolded repo's catalog.
- **Route determination is derived, never inferred from names.** `e2e/catalog.md` has exactly three columns and carries no route, and a page object's class name is not its route (`TodoPage` was scanned from `/todomvc`). `author-scenario` therefore takes the route from the sentence, else from an existing `Given I am on the '<route>' page` parameter or a page object's recorded scan URL, else asks the user once and persists nothing — and the ordered route list it derives is what selects `e2e/features/<route-slug>.feature` vs `e2e/features/flows/<flow-slug>.feature`.
- `author-scenario` owns its step files by a first-line marker (`// author-scenario: skill-owned. page-scanner never writes here.`), not by path: `e2e/steps/authored.steps.ts` and `e2e/steps/todo.steps.ts` normally, plus the fallback `e2e/steps/todo.authored.steps.ts` when an unmarked `todo.steps.ts` already exists (scanner-owned — the skill leaves it untouched and prints the `Collision: ` line).
- The navigation phrase must stay in the `I am ` form because `scaffold-bdd`'s `G2` derives the keyword from the phrase.
- `docs/examples/author-scenario/` is a release artifact (ships to installed users) and is hand-written, kept honest only by `validate_author_scenario.py`.
- `skills/web-tester/SKILL.md` is deliberately not wired to `author-scenario`; discovery is via the skill's own frontmatter `description`.
- **Why `playwright-bdd` + Gherkin, not plain `Playwright Test` or `Cucumber.js`.** Plain `Playwright Test` has no reusable phrase catalog: every scenario re-writes its own selectors and assertions inline, so there is nothing for `page-scanner` to build and nothing for authoring to read back. `Cucumber.js` has the phrase-catalog shape but its own runner, reporter, and trace/video pipeline, separate from Playwright's — `playwright-bdd` instead compiles `.feature` files into native Playwright Test files at generation time, so the project keeps exactly one runner, one reporter, and one trace pipeline, and `e2e/catalog.md` stays the single reusable phrase dictionary both `page-scanner` and authoring read and write.
- **The dictionary lives in the target repo under test, never in this plugin repo.** `e2e/catalog.md`, `e2e/pages/*.ts` page objects, and `e2e/steps/*.ts` step definitions are all written by `page-scanner`/`scaffold-bdd` into the target repo under test — this plugin repo ships no committed `e2e/` tree of its own (see the `scaffold-bdd` bullet above); `docs/examples/` is the only mirror of that shape, kept honest by the validator scripts.
- **The authoring/execution split: LLM involvement stops at authoring time.** `page-scanner` and scenario authoring both run with an LLM/MCP in the loop, but everything they produce — `e2e/catalog.md`, page objects, step definitions, `.feature` files — is static text once written. CI never re-invokes a model: it runs `bddgen` to compile `.feature` files into native Playwright specs, then `playwright test` to execute them, so every CI run is zero-LLM and fully deterministic.
- **This is a hybrid package (skill + subagent + inline MCP wrapper), and the marketplace `category` stays `"skill"` deliberately.** The dispatch payload to `Seretos/agent-marketplace` sends `category: "skill"` even though the package also ships `agents/page-scanner.md` and an inline `mcpServers.playwright` block, because the marketplace's install/discovery flow is skill-first — a user installs "a skill for E2E testing," and the subagent plus MCP wrapper are implementation details that come along for the ride, not a separate listing.
